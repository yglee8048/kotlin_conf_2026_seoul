Step 3 · ThreadLocal 전파

thread local 전파하기 ① 요청 진입 시 컨텍스트 세팅

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class CallContextFilter : OncePerRequestFilter() {

    override fun doFilterInternal(request, response, filterChain) {
        val context = CallContext(
            traceId = request.getHeader("X-Trace-Id") ?: newTraceId(),
            channel = Channel.from(request.getHeader("X-Channel")),
            ...
        )
        try {
            CallContextHolder.set(context)
            MDC.put("traceId", context.traceId)
            filterChain.doFilter(request, response)
        } finally {
            CallContextHolder.clear()   // 톰캣 스레드도 재사용된다 — 원복 필수
            MDC.clear()
        }
    }
}
Step 3 · ThreadLocal 전파

thread local 전파하기 ② 캡처 → 주입 → 원복

class CallContextTaskDecorator : TaskDecorator {

    override fun decorate(runnable: Runnable): Runnable {
        // 1. 캡처 — 여기는 "제출하는" 스레드 (톰캣)
        val capturedContext = CallContextHolder.get()
        val capturedMdc = MDC.getCopyOfContextMap()

        return Runnable {
            // 2. 주입 — 여기는 "실행하는" 스레드 (풀)
            val previousContext = CallContextHolder.get()
            val previousMdc = MDC.getCopyOfContextMap()
            try {
                CallContextHolder.set(capturedContext)
                applyMdc(capturedMdc)
                runnable.run()
            } finally {
                // 3. 원복 — 풀 스레드는 재사용된다. 안 지우면 다음 요청이 남의 traceId 를 본다
                CallContextHolder.set(previousContext)
                applyMdc(previousMdc)
            }
        }
    }
}

fun getHomeItemsV4(userId: UserId): CompletableFuture<List<HomeItem>> {
    // 코어뱅킹 조회는 blocking 그대로 — 뒤의 두 조회가 여기 의존하므로 어차피 기다려야 한다
    val accounts = coreBankAdapter.getAccounts(userId)
    return composeRest(userId, accounts)
}

private fun composeRest(...): CompletableFuture<List<HomeItem>> {
    val homeCardInfoFuture   = CompletableFuture.supplyAsync({ ... }, homeInfoTaskExecutor)
    val openBankBalanceFuture = CompletableFuture.supplyAsync({ ... }, openBankingTaskExecutor)
    userLogRepository.saveEventAsyncV3(userId, UserEvent.GET_HOME)

    // join() 대신 thenCombine — 병렬 결과를 앉아서 기다리는 스레드가 없다
    return homeCardInfoFuture.thenCombine(openBankBalanceFuture) { infos, balances ->
        assemble(accounts, infos, balances)   // 조립 로직이 콜백 안으로 끌려 들어왔다
    }
}

class CallContextElement(
    private val callContext: CallContext? = CallContextHolder.get(),        // 캡처
) : ThreadContextElement<CallContext?> {
    override fun updateThreadContext(ctx: CoroutineContext): CallContext? =
        CallContextHolder.get().also { CallContextHolder.set(callContext) } // 주입 — 재개될 때마다
    override fun restoreThreadContext(ctx: CoroutineContext, old: CallContext?) =
        CallContextHolder.set(old)                                          // 원복 — 중단될 때마다
}

코루틴에서는 더 위험하다

withContext(Dispatchers.IO) { insertHistory() }
@Async 같은 시각적 신호조차 없이 스레드가 바뀐다.
규칙: 트랜잭션 경계 안에서 스레드를 넘기지 않는다.

대안

커밋 이후로 미루기 — @TransactionalEventListener(AFTER_COMMIT)
유실이 안 되면 outbox 패턴.

실전 팁 ②

CoroutineScope 는 Bean 으로

fire-and-forget 용 스코프를 매번 만들지 말고 — 싱글턴으로 하나

@Component
class ApplicationCoroutineScope : CoroutineScope {
    private val supervisorJob = SupervisorJob()                       // ①
    private val exceptionHandler = CoroutineExceptionHandler { ctx, t -> log.warn(...) }  // ②

    override val coroutineContext =
        supervisorJob + Dispatchers.IO + CoroutineName("app-scope") + exceptionHandler

    @PreDestroy                                                       // ③
    fun shutdown() = runBlocking {
        withTimeoutOrNull(5_000) { supervisorJob.cancelAndJoin() }    // 취소를 보내고, 정리까지만 기다린다
    }
}

① SupervisorJob

일반 Job 이면 작업 하나의 실패가 다른 API 의
코루틴까지 취소시킨다. 반드시 Supervisor 로.

② 스코프 단위 예외 처리

@Async 는 전역 핸들러 하나뿐이었다.
여기선 스코프마다 붙는다. 힙도 스코프 하나로 절약.

③ @PreDestroy 취소 전파

서버 종료 시 실행 중인 코루틴에 취소를 전파.
executor 의 “기다리기만”과 다르다.

전체 리뷰 — 스레드는 이렇게 흘러왔다

톰캣 스레드가 1.84s 통째로
2~3. Future 병렬 P

suspend 로 반납
IO 64 천장

blocking 그대로인데 unmount — 코드 0줄 수정
9~11. VT + 코루틴 V
톰캣 VT 코어뱅킹
suspend 반납
구조적 동시성 + 상한

남은 이유 — 수명·실패·취소의 구조화, 컨텍스트 전파, 간결한 코드 — 는 그대로다. blocking MVC 에서도 코루틴은 여전히 유효하다.
번외 · non-blocking

non-blocking 세계에서는 더 강력하다

WebFlux 의 문제는 성능이 아니라 코드였다 — 코루틴이 그걸 지운다

// WebFlux (Reactor) — operator 체인
fun getHomeItems(userId: UserId): Mono<List<HomeItem>> =
    coreBank.getAccounts(userId)
        .flatMap { accounts ->
            Mono.zip(
                infoRepo.getInfos(accounts.ids()),
                openBanking.getBalances(accounts.obIds()),
            ).map { (infos, balances) ->
                assemble(accounts, infos, balances)
            }
        }
        .contextWrite { ... }   // 컨텍스트도 수동으로
// WebFlux + Coroutine — 같은 non-blocking
suspend fun getHomeItems(userId: UserId): List<HomeItem> =
    coroutineScope {
        val accounts = coreBank.getAccounts(userId)  // awaitBody
        val infos    = async { infoRepo.getInfos(accounts.ids()) }
        val balances = async { openBanking.getBalances(accounts.obIds()) }
        assemble(accounts, infos.await(), balances.await())
    }
// 스레드 hop 이 몇 번이든 위에서 아래로 읽힌다

컨텍스트 전파가 공짜

Reactor Context ↔ CoroutineContext 가 자동 변환된다 (ReactorContext element). ThreadLocal 이 없는 세계에서 코루틴 컨텍스트가 요청을 따라다닌다 — MDC·tracing 이 accessor 로 그대로.

Flow 로 스트리밍까지

SSE·WebSocket 같은 long-lived response 도
Flux operator 지옥 없이 Flow 로 순차 코드처럼 쓴다.
